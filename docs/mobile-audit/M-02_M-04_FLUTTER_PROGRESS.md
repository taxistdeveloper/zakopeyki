Утилиты: `bin/dev_router.php` (локальный `php -S` с отдачей статики), `bin/seed_mobile_test_user.php` (только не-production). `.htaccess` закрывает `mobile/`.

**Flutter-приложение** `mobile/app` (iOS + Android, bundle id `kz.zakopeyki.zakopeyki`): вход + 2FA, восстановление сессии, лента с поиском (debounce), фильтр по типу, бесконечная прокрутка, pull-to-refresh, карточка товара с галереей, избранное, профиль, переключение языка RU/KK/EN, состояние «Скоро открытие» с входом для участников теста. ## Инкремент 2 (2026-11-10): регистрация, сброс пароля, Sign in with Apple

**Backend**
- `app/Services/Auth/AccountService.php` — единая логика для сайта и API: регистрация (валидация, бонус, реферал, конкурсы, письмо подтверждения), письмо сброса пароля, вход через внешнего провайдера (поиск по ID провайдера → связывание по **подтверждённому** провайдером email → создание аккаунта). `AuthController` (web) переведён на сервис — дублирования нет; web-регистрация проверена end-to-end (CSRF, редирект, бонус).
- `app/Services/Auth/IdTokenVerifier.php` — проверка ID-токенов Apple/Google: RS256 по JWKS провайдера (кэш 6 ч в `storage/cache`), `iss`, `aud`, `exp/iat`, nonce (Apple). Отклоняются: чужое приложение, чужой издатель, просроченный, повторно использованный nonce, неизвестный ключ, `alg=none`, подмена payload.
- Новые endpoint'ы: `POST /auth/register` (201, сразу выдаёт токены), `POST /auth/forgot-password` (одинаковый ответ для любого email), `POST /auth/apple`, `POST /auth/google` (выключен, пока не заданы client id), `POST /me/email/resend-verification`. 2FA соблюдается и для входа через Apple/Google. Колонка `users.apple_id` создаётся автоматически.
- `config/mobile.php` — публичные идентификаторы: bundle id для Apple (`kz.zakopeyki.zakopeyki`), client id Google (env `GOOGLE_MOBILE_CLIENT_IDS`).
- Бонус за регистрацию отдаётся как `registration_bonus_points` (баллы, не тенге).

**Приложение**: экраны регистрации (с принятием соглашения и ссылкой на него) и восстановления пароля, ссылки на входе, кнопка Sign in with Apple (только iOS, одноразовый nonce, обработка отмены), entitlement `com.apple.developer.applesignin` в `ios/Runner/Runner.entitlements`.

**Проверки**: `tools/run_mobile_auth_tests.php` 22/22; все 27 backend-раннеров зелёные; curl-смоук новых endpoint'ов; `flutter test` 17/17 (в т.ч. найден и исправлен перенос строки «Нет аккаунта?» на узких экранах); integration-тест регистрации на симуляторе — см. итог в отчёте сессии.

**Не проверено / требует владельца**: реальный вход через Apple — нужен аккаунт Apple Developer с включённой возможностью Sign in with Apple для `kz.zakopeyki.zakopeyki` и подписанная сборка (в симуляторе без команды разработчика Apple выдаёт ошибку — приложение показывает «Вход через Apple недоступен»). Google-вход в приложении — после создания OAuth-клиентов в Google Cloud. Риск: связывание по email (как и в существующем web-входе через Google) — осознанное решение, подтверждено провайдером `email_verified`.

**App Store 5.1.1(v)**: раз в приложении появилась регистрация, обязательна **возможность удалить аккаунт в приложении**. Текущее удаление на сайте не работает для аккаунтов без пароля (Apple/Google) и не учитывает баланс/открытые сделки (SECURITY_AUDIT S5) — это следующая обязательная задача перед публикацией.

## Инкремент 4 (2026-11-10): удаление аккаунта (App Store 5.1.1(v), Google Play)

**Решение: обезличивание, а не физическое удаление.** Проверка БД показала: на `users` ссылаются ~60 колонок, но FK с каскадом есть только у 6 таблиц (товары, ставки, бонусы, уведомления, try-on). Прежний `DELETE FROM users` удалял объявления каскадом, а заказы, платежи и движения кошелька оставались «висячими» — у второй стороны сделки пропадал контрагент.

`app/Services/Auth/AccountDeletionService.php` (общий для сайта и API):
- **Блокеры**: деньги на кошельке (доступные + удержанные) и незавершённые сделки (покупатель или продавец, статус не `completed/refunded/partial_refunded/cancelled`). Пока они есть, удаление не выполняется.
- **Удаление**: имя, email (→ `deleted+ID@deleted.invalid`), телефон, ИИН/БИН, адреса, био, аватар, пароль, 2FA, токены сброса/подтверждения, связи Google/Apple стираются; аккаунт блокируется (`blocked_reason = account_deleted`, `deleted_at`); объявления → `archived`; избранное, подписки, истории, уведомления, AI-память удаляются; Seller API ключи отзываются; все мобильные сессии отзываются; файлы аватара, историй и KYC удаляются, данные Try-On — через `TryOnService::purgeUser`. Заказы, платежи, кошелёк, отзывы остаются в обезличенном виде. Тот же email можно зарегистрировать снова.
- **Подтверждение**: аккаунт с паролем — пароль; без пароля (Google/Apple) — вход не старше 10 минут (раньше такие аккаунты на сайте удалить было нельзя — S5 закрыт).

API: `GET /me/deletion` (блокеры + способ подтверждения), `POST /me/delete` (`confirm` + `password`; 403 `reauth_required`; 409 `deletion_blocked` с блокерами). Сайт: `ProfileController::deleteAccount` переведён на сервис; `Auth::login` запоминает время входа.

Приложение: Профиль → «Удалить аккаунт» → экран с последствиями, блокерами, паролем или повторным входом, подтверждением.

Проверки: `tools/run_account_deletion_tests.php` 18/18; все 28 backend-раннеров зелёные; HTTP-смоук API; web-удаление с CSRF (неверный пароль → форма, верный → аккаунт обезличен); `flutter test` 20/20; integration-сценарий «регистрация → профиль → удаление» на Android.

**Требует владельца (до публикации в App Store):**
1. **Отзыв токенов Sign in with Apple** при удалении (требование Apple для приложений с SIWA): нужен ключ Sign in with Apple (`.p8`, Key ID, Team ID) из Apple Developer; сервер должен при входе обменивать `authorization_code` на refresh-токен Apple и вызывать `https://appleid.apple.com/auth/revoke` при удалении. Без ключа не реализовано.
2. Срок хранения обезличенных финансовых записей и текст в политике конфиденциальности (Q11).
3. На сайте в режиме заглушки пользователь без бета-доступа не может открыть профиль (и удаление) — в приложении удаление доступно.
4. Публичная web-страница с инструкцией удаления (обязательна для Google Play Data safety).

## Инкремент 6 (2026-11-11): корзина, оформление, оплата, заказы (M-07)

**Корзина** (`app/Services/Cart.php`): для вошедшего пользователя хранится в БД (`user_cart_items`) — **общая для сайта и приложения** и между устройствами; гостевая корзина сайта переносится в аккаунт при входе. Логика (доступность, остатки, «свой товар») не менялась.

**Оформление** — `Order::createEscrow` / `createEscrowCart` без изменений (суммы, сбор Safe Deal 3%, остатки, оплата кошельком/картой). API: `GET /cart`, `POST /cart/items`, `/cart/items/{id}/qty|remove`, `/cart/clear`, `GET /checkout/options` (режимы сделки с суммами, способы получения, оплаты, баланс), `POST /checkout` → `order_ids` + `payment {status: paid|pending, payment_url}`. Доставка CDEK (ПВЗ получателя) — пока на сайте (`cdek_on_website`).

**Оплата картой из приложения:** `GET /payments/halyk/app/{token}` — та же форма Halyk без web-сессии (доступ — одноразовый токен intent 128 бит; `no-store`, `no-referrer`); возврат из банка → `/payments/app-return` → `zakopeyki://payment-result`. Приложение открывает форму через `flutter_web_auth_2` (ASWebAuthenticationSession / Custom Tabs) и **не доверяет** результату возврата — статус заказа берёт с сервера (оплату подтверждает только postLink, M-01). Пока заказ «ожидает оплаты», экран заказа опрашивает сервер.

**Заказы:** `GET /orders?role=buying|selling`, `GET /orders/{id}`, действия `ship` (трек), `delivered`, `confirm`, `cancel`, `dispute` (причина + комментарий ≥10 символов) — через EscrowService/ReturnService; поле `actions` вычисляется на сервере по роли и статусу. Переговоры по возврату и арбитраж — на сайте.

**Найдено и исправлено (существующая ошибка сайта):** `new Payment()` внутри транзакции выполнял DDL (`CREATE TABLE IF NOT EXISTS`) → MySQL делал неявный COMMIT → отмена неоплаченного заказа в «свежем» запросе падала, успев частично записать изменения (заказ «отменён», а платёж «ожидает», остаток не возвращён). Исправлено: `Payment::ensureTable` не выполняет DDL внутри транзакции; модель создаётся до транзакции. **Риск:** около 50 моделей выполняют DDL в конструкторах — аналогичные случаи возможны; рекомендуется перейти на миграции (P3).

**Приложение:** вкладка «Корзина» со счётчиком; на карточке «В корзину» и «Купить»; оформление: выбор Безопасная сделка / напрямую (с пояснениями и суммами сервера), способ получения, оплата картой или кошельком (с балансом); «Мои заказы» (Покупки/Продажи), карточка заказа с действиями и диалогами (трек-номер, причина спора).
