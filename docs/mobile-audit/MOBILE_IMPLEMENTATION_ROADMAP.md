# MOBILE_IMPLEMENTATION_ROADMAP — этапы реализации

> MASTERING-00 · 2026-11-09. **Сроки не обещаются.** Размеры даны в человеко-неделях (чел.-нед.) как диапазоны.
> Допущения диапазонов: 1 full-stack разработчик (PHP + TS) с Cursor/Claude, знающий кодовую базу, + привлекаемый дизайнер и QA по необходимости; без крупных изменений требований; решения из RISKS_AND_OPEN_QUESTIONS приняты до начала соответствующего этапа. Неопределённость высокая (±50%), особенно для live/IAP/stores review. Каждый этап завершается отдельным согласованием владельца.

## Критический путь до MVP

**MVP (покупатель + базовый продавец):** вход/регистрация, лента и поиск с фильтрами, карточка, избранное, подписки, создание объявления с фото, корзина, оформление (обычная покупка и Safe Deal) с оплатой Halyk, заказы и подтверждение получения/спор, доставка CDEK, чат, уведомления + push, профиль, удаление аккаунта, KK/RU (EN — по решению Q5).

```
M-01 Security ─► M-02 API foundation ─► M-03 Catalog API ─► M-05 App: auth+catalog ─► M-06 Listings
                                    └─► M-04 App shell (параллельно с M-03)                │
M-07 Cart/Checkout/Orders/Delivery ◄────────────────────────────────────────────────────────┘
M-07 ─► M-08 Chat + Notifications + Push ─► M-09 Hardening + store release (MVP)
```
Ориентир MVP: **~22–40 чел.-нед.** суммарно (backend ~55%, клиент ~45%).

## Этапы

### M-01. Security hardening backend (блокер)
- **Цель:** закрыть P0 из BACKEND_GAP_ANALYSIS (B0.1–B0.8).
- **Результаты:** исправленный postlink с тестами подделки; env-конфигурация; починенное пополнение; блокировки в escrow; закрытые загрузки.
- **Зависимости:** решение владельца по prod-значениям флагов; доступ к тестовому терминалу Halyk.
- **Модули:** `PaymentController`, `HalykEpay/*`, `EscrowService`, `OrderController`, `AuthController`, `UploadHelper`, webhook-сервисы.
- **Риски:** регресс web-оплат → нужен прогон всех `tools/run_*_tests.php` и ручной сценарий оплаты в тестовом режиме.
- **Специалисты:** backend PHP, security review.
- **Приёмка:** неаутентифицированный POST на postlink не меняет ни одного баланса/статуса (автотест); `settle()` идемпотентен при параллельных вызовах (тест); KYC-файлы недоступны по прямому URL.
- **Объём:** 2–4 чел.-нед.

### M-02. Фундамент мобильного API
- **Цель:** B1.1–B1.5, B1.17 (минимум), B1.20.
- **Результаты:** `/api/mobile/v1`, токены и устройства, Google/Apple вход, envelope, ошибки, rate limit, идемпотентность, OpenAPI с CI-проверкой, `/config`, Sentry на сервере, PHPUnit в CI.
- **Зависимости:** M-01; решение Q2 (Apple/Google аккаунты разработчика — создаёт владелец).
- **Риски:** смешение cookie- и bearer-авторизации; совместимость с stub mode.
- **Приёмка:** OpenAPI валиден; контрактные тесты auth (вход, 2FA, refresh-ротация, reuse detection, logout-all); 0 секретов в клиенте.
- **Объём:** 4–6 чел.-нед.

### M-03. API каталога, карточек, медиа
- **Цель:** B1.6–B1.9.
- **Результаты:** лента/каталог/поиск с курсором и фильтрами, категории, карточка, профиль продавца, отзывы, избранное, подписки, upload с превью.
- **Риски:** производительность поиска (`LIKE` → FULLTEXT; поведение FULLTEXT для казахских словоформ — проверить).
- **Приёмка:** p95 ответа ленты < 500 мс на тестовых данных ~10k объявлений [целевое значение для утверждения]; размер ответа первой страницы < 100 KB без изображений.
- **Объём:** 3–5 чел.-нед.

### M-04. Каркас приложения (параллельно с M-03)
- **Цель:** Expo-проект, навигация, дизайн-токены, i18n (kk/ru/en-заглушка), API-клиент из OpenAPI, secure storage, Sentry, EAS Build preview, CI (lint/typecheck/test).
- **Предварительно:** stack spike (MOBILE_STACK_COMPARISON §5) — 3–5 дней.
- **Приёмка:** сборки iOS/Android устанавливаются через TestFlight/Internal testing; crash-репорт приходит в Sentry; переключение языка без перезапуска.
- **Объём:** 2–3 чел.-нед.

### M-05. Приложение: вход, каталог, карточка, избранное, профиль
- **Зависимости:** M-02, M-03, M-04.
- **Приёмка (E2E Maestro/Detox):** гость → лента → поиск с фильтром → карточка → вход → избранное → подписка; работа на font scale 200%; офлайн-просмотр кэша.
- **Объём:** 3–5 чел.-нед.

### M-06. Объявления продавца
- **Цель:** B1.10 + клиент: создание/редактирование/удаление, камера/галерея, сжатие, фоновая загрузка, верификация (AML) и правила, лимиты business-пакета (отображение).
- **Риски:** вынос логики из `ProfileController` без регресса web (покрыть тестами до рефакторинга).
- **Приёмка:** объявление, созданное в приложении, идентично web-объявлению; загрузка 10 фото по 3G-профилю с возобновлением.
- **Объём:** 3–5 чел.-нед.

### M-07. Корзина, оформление, оплата, заказы, доставка
- **Цель:** B1.11–B1.13, B1.18 + клиент (Safe Deal vs обычная покупка, preview сумм, Halyk в Custom Tabs/SFSafariViewController, статусы, подтверждение получения, 24-часовое окно, спор/возврат, CDEK ПВЗ на карте, трекинг).
- **Зависимости:** M-01 (обязательно), Q3/Q4.
- **Риски:** возврат из платёжной страницы в приложение; двойные нажатия → идемпотентность; расхождение правил окна спора (см. RISKS R6).
- **Приёмка:** сценарии в **тестовом режиме Halyk** на staging: успешная оплата, отказ, повторный callback, отмена, подтверждение, спор, частичный возврат; суммы на клиенте совпадают с серверными расчётами.
- **Объём:** 5–8 чел.-нед.

### M-08. Чат, уведомления, push
- **Цель:** B1.14, B1.15 + клиент; deep links (B1.19).
- **Приёмка:** push о новом сообщении/статусе заказа приходит на iOS и Android в фоне и при закрытом приложении; тап открывает нужный экран; отписка по категориям.
- **Объём:** 3–5 чел.-нед.

### M-09. Hardening и выпуск MVP
- **Цель:** удаление аккаунта (B1.16), политика конфиденциальности/Data safety/Privacy Nutrition Labels, App Privacy manifest, скриншоты/описания KK/RU, доступность, нагрузочный тест API, бета-тестирование, релиз.
- **Приёмка:** чек-лист сторов (ниже) пройден; crash-free sessions ≥ 99.5% в бете [цель для утверждения]; критические E2E зелёные.
- **Объём:** 2–4 чел.-нед. + время ревью сторов.

## Требования сторов (подготовить, аккаунты не создавались)

**Apple App Store:** Apple Developer Program (организация, D-U-N-S); Sign in with Apple при наличии Google-входа (4.8); удаление аккаунта в приложении (5.1.1(v)); Privacy Nutrition Labels и Privacy Manifest (`PrivacyInfo.xcprivacy`, required-reason API); ATT, если есть трекинг; IAP для цифровых товаров/услуг, потребляемых в приложении (3.1.1) — **см. Q3**; физические товары — внешняя оплата допустима (3.1.3(e)/3.1.5); модерация UGC: жалобы, блокировка пользователей, фильтрация (1.2) — частично есть (жалобы), **блокировки пользователей между собой нет**; демо-аккаунт для ревью; актуальный Xcode/iOS SDK.

**Google Play:** аккаунт разработчика (организация, верификация); targetSdk 36 (с 31.08.2026); Data safety form; ссылка удаления аккаунта (в приложении и web); политика UGC; Play Billing для цифровых товаров (аналогично Q3); App Signing; закрытое тестирование (для новых личных аккаунтов — требования к числу тестировщиков [?] проверить актуальные правила).

**Общее:** политика конфиденциальности (есть `/privacy`, `/data-policy` — проверить полноту для мобайла), пользовательское соглашение (`/offer`), возрастной рейтинг, контакты поддержки.
