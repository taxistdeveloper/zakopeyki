## A. Резюме аудита

1. **Платформа** — самописный PHP MVC без фреймворка, Composer и ORM; MySQL 8 через PDO; Redis опционален; фронтенд — PHP-шаблоны + один vanilla `app.js` + Tailwind CDN. Архитектура стабильна и позволяет добавить модуль как ещё один «вертикальный срез» (Controller → Policy/Service → Model), по образцу платных услуг (`Boost`, `Ads`, `MassPush`).
2. **В проекте уже есть розыгрыш** — простой розыгрыш в прямом эфире (`/streams/live/giveaway/*`): случайный выбор `ORDER BY RAND()`, результат не сохраняется, журнала нет, хост может «перетягивать» несколько раз, все данные удаляются после эфира, **выключателя нет**. ⚠️ Это публично доступная механика случайного определения победителя без юридического заключения.
3. **Реферальная программа существует в минимальном виде**: код = логин/ID, `users.referred_by`, 500 бонусных баллов пригласившему **сразу при регистрации** без квалификации, без отмены, без антифрода, без админ-настроек. Тексты оферты расходятся с кодом. ⚠️ Подключение конкурсов к ней в нынешнем виде усилит накрутку.
4. **Ни одно внутреннее действие (подписка, лайк, избранное, комментарий) нельзя проверить на прошлый момент времени**: отмена — жёсткий `DELETE`, истории событий нет, лайки — анонимный счётчик только в эфирах, комментарии есть только в эфирах и удаляются. Для проверяемых условий нужен собственный журнал событий модуля.
5. **Нет**: блокировки пользователей, роли модератора, делегирования доступа сотрудникам магазина, жалоб на что-либо кроме объявлений, подтверждения email/телефона, rate limiting на входе/регистрации, push/Telegram-уведомлений, локального генератора QR, UTM-атрибуции, механизма миграций.
6. **Есть и переиспользуемо**: глобальный CSRF, prepared statements, `Setting` (флаги функций), `ActivityLogger` (аудит в БД), `Notification` (in-app), `Mail`, `Bonus::award()` (идемпотентный по `uq_award`), `RateLimiter` (AI), `SiteVisit`/`product_views` (уникальные посетители), `SupportTicket` (жалобы на объявления), паттерн Policy + `idempotency_key`.

**Вывод о готовности:** технически реализовать MVP модуля в текущей архитектуре можно, без переписывания платформы. Начинать разработку (MASTERING-02) **нельзя** до: (а) юридического заключения по механикам определения результата; (б) решения по правилам реферальной программы; (в) закрытия критичных проблем безопасности, которые напрямую влияют на модуль (раздел F, пункты F-1…F-4).

## D. Аудит реферальной программы

**Статус: 🟡 минимальная «оплата за регистрацию».**

| Аспект | Факт |
|---|---|
| Код приглашения | Отдельной таблицы нет. Код = `users.login`, иначе числовой `id` (`User::referralCodeFor`, `findByReferralCode`). Ссылка `/register?ref=<code>` (`User::referralUrlFor`). ⚠️ Смена логина ломает ранее розданные ссылки |
| Привязка | `users.referred_by` (только runtime-ALTER, `User.php:39`; индекс `users_referred_by_idx`). `User::setReferredBy` пишет только если пусто → **перепривязка невозможна**; самоприглашение блокируется |
| Захват | `AuthController::captureReferralFromRequest()` (`?ref=`/`POST ref`, `^[a-zA-Z0-9_]{1,50}$`) → `$_SESSION['referral_ref']`; вызывается только в `registerForm`, `register`, `googleRedirect` |
| Окно атрибуции | Время жизни PHP-сессии; cookie и срока нет; **последний `ref` перезаписывает предыдущий**. Переход на любую другую страницу с `?ref=` не фиксируется |
| Квалификация | ❌ Нет: начисление сразу после создания аккаунта (`applyReferralBonus` в `register()` стр. 192 и `googleCallback()` стр. 314) |
| Начисление | `Bonus::awardReferral()` — `AMOUNT_REFERRAL = 500` баллов (константа), уведомление `bonuses.notify_referral`; идемпотентность через `uq_award` |
| Подтверждение / pending | ❌ |
| Отмена / корректировка | ❌ (в `Bonus` нет методов списания) |
| История | Общий `bonus_transactions` (type `referral`), страница `/bonuses` |
| Баланс | `bonus_balances.balance`; баллы ≠ деньги, вывода нет (соответствует UI-подсказке) |
| Выплаты | ❌ |
| Антифрод | ❌ (нет IP/устройство/скорость; нет подтверждения email) |
| Админ-настройки | ❌ |
| UI | Вкладка профиля `referral` (`app/Views/profile/index.php:808+`): ссылка, копирование, счётчик, последние 30 приглашённых |

**Расхождения документации и кода:** оферта (`lang/ru.php` ~2558, 2606–2609, 2634) говорит о бонусах за KYC, о трате бонусов на купоны и до 50% стоимости платных услуг, о праве оператора аннулировать бонусы. В коде ничего из этого нет, зато есть бонусы за подписчиков и объявления, которых нет в оферте. `ARCHITECTURE_AUDIT.md` помечает «Wallet / bonuses ✅» — это слишком широко.

**Как модулю использовать программу без параллельной системы начислений:**
1. Модуль **не начисляет** реферальное вознаграждение сам. Он только (а) прокидывает `ref` с публичной страницы акции в тот же `$_SESSION['referral_ref']` (единый ключ, единая логика `captureReferralFromRequest` — вынести в общий хелпер, а не копировать) и (б) пишет **свою** запись атрибуции «акция → переход → регистрация» для аналитики организатора.
2. Начисление остаётся в `AuthController::applyReferralBonus` → `Bonus::awardReferral`. Модуль читает статусы по `bonus_transactions(type='referral', ref_id=<new_user_id>)`.
3. **Блокирующий вопрос D-1:** текущие правила (500 баллов сразу, без квалификации) не задокументированы как утверждённые и не совпадают с офертой. Без этого нельзя показывать участнику «статус вознаграждения» и нельзя усиливать поток приглашений через конкурсы — это прямой канал накрутки фейковых регистраций. Нужно решение: какие условия квалификации, срок атрибуции, правило first/last touch, есть ли pending/отмена.

**Безопасно использовать для аналитики конкурсов:** уникальные посетители по `zk_vid` (с собственной таблицей просмотров акции по образцу `product_views`), регистрации (`users.created_at` + атрибуция модуля), подписки на организатора (текущее состояние + журнал модуля с момента запуска), покупки у организатора (`orders`), реферальные начисления (`bonus_transactions`).

**Воронка без двойного учёта (предложение):** просмотр (все) → уникальный посетитель (`visitor_key`) → переход по ссылке участника (`contest_ref_visits`, UNIQUE `(contest_id, visitor_key, ref_user_id)`) → регистрация (`users`, атрибутирована один раз) → подтверждённая регистрация (**недоступно**, пока нет верификации) → квалифицированный реферал (**по правилам D-1**) → подтверждённое участие (`contest_entries.status='confirmed'`) → последующая активность (подписка/заказ у организатора после даты участия). Каждый этап — отдельный счётчик со своим ключом уникальности; конверсии считаются только от предыдущего этапа.

| CSRF | ✅ | Глобально в `Router::dispatch` для POST (`Csrf::enforce`, `hash_equals`, поле `_csrf` / `X-CSRF-TOKEN`). Исключения: 4 вебхука, `/api/v1/micro-tasks/*` ⚠️ (сессия без CSRF), `/api/v1/business/*` при Bearer |
| SQL injection | ✅ в основном | Prepared statements. `Model::all($order)` вставляет аргумент в SQL без проверки — не вызывать с пользовательским вводом |
| XSS | 🟡 | Ручной `htmlspecialchars` (~3100 вызовов), без автоэкранирования; `HtmlSanitizer` только в админ-библиотеке/задачах. Для описаний акций нужен `HtmlSanitizer` или plain text |
| Rate limiting | 🟡 | Только AI `RateLimiter` и лайки эфира (в сессии, обходится). Нет на логин, регистрацию, сброс пароля, подписки, вступление в розыгрыш ⚠️ |
| Контроль доступа | 🟡 | Проверки в каждом методе вручную, без middleware. Модулю нужна собственная Policy с проверкой владения в каждом действии |
| Загрузка файлов | ✅ | `UploadHelper` (allowlist, finfo, magic bytes) — использовать для изображений призов |
| Заголовки | 🟡 | nosniff, X-Frame-Options, Referrer-Policy; **нет CSP и HSTS** |
| Защита каталогов (`.htaccess`) | ⚠️ | Не закрыты `bin/`, `logs/`, `tmp/`, `.git/`, `_vas11_extract/`, `_vas12_extract/`, корневые `*.txt/*.md/*.json/*.mp3`, `tmp_home.html`. Из 23 скриптов `bin/*.php` только 6 проверяют `PHP_SAPI`; среди незащищённых — сид-скрипты демо-аккаунтов |
| Платежи | ⚠️ | `config/app.php: allow_simulated_payments => true` (включён симулированный ввод/вывод) |
| Идемпотентность | ✅ паттерн | `idempotency_key` UNIQUE в платных услугах; `uq_award` в бонусах; `FOR UPDATE` в 45 местах. Кошелёк без ключа; `EscrowService::settle()` проверяет статус до транзакции без блокировки строки ⚠️ |
| Модерация | 🟡 | Статусы модерации только у рекламы/пушей/бизнес-заявок; у товаров pre-moderation нет |
| Жалобы | 🟡 | Только на объявления через `support_tickets` |
| Блокировки пользователей | ❌ | Нет флага бана; только удаление аккаунта, AML-блок, лимит оборота |
| Журналирование | ✅ | `activity_logs` с IP/UA; подписки/избранное/эфиры не логируются |
| Персональные данные | 🟡 | `site_visits` и `activity_logs` хранят IP/UA без описанного срока хранения; политики удаления нет. Публикация данных победителей потребует согласия |
| Удаление аккаунта | ⚠️ | `User::deleteAccount` — жёсткое удаление; `user_follows` без FK оставляет «сирот». Для акций нужна стратегия: участие сохраняется обезличенно |

**Проблемы, которые блокируют модуль (исправить до или в начале MASTERING-02, отдельным согласованным пакетом):**
- **F-1** Нет rate limiting на регистрацию/вход → массовые фейковые аккаунты для участия и рефералов.
- **F-2** Нет подтверждения email/телефона → нельзя определить «подтверждённую регистрацию» и «одного человека — одно участие».
- **F-3** Нет механизма блокировки пользователя → антифрод не может применить санкции.
- **F-4** Розыгрыш в эфире: нет флага отключения, результат не сохраняется, повторный draw возможен.

**Общие проблемы платформы (вне модуля, сообщаю для решения):** открытые `bin/`, `.git/`, `logs/` и др. через веб; TOTP-секрет уходит на `api.qrserver.com`; `allow_simulated_payments=true`; CSRF-исключение для сессионного micro-tasks API; гонка в `EscrowService::settle()`.

## Жизненный цикл акции

`draft → pending_moderation → approved → scheduled → active → entries_closed → result_processing → results_published → fulfilment → completed`; доп.: `rejected`, `suspended`, `cancelled`, `disputed`.

| Переход | Организатор | Модератор (`contests`) | Админ | Серверная проверка |
|---|---|---|---|---|
| draft → pending_moderation | ✅ | — | ✅ | Валидация полей, тип и метод итогов включены флагами |
| pending_moderation → approved / rejected | — | ✅ | ✅ | Причина отклонения обязательна |
| approved → scheduled / active | авто (cron по `starts_at`) | — | ✅ | Время сервера |
| active → entries_closed | авто по `ends_at` | — | ✅ | Только cron/сервер |
| entries_closed → result_processing → results_published | ✅ запуск (жюри: ввод решений) | — | ✅ | Однократно, `FOR UPDATE`, журнал |
| → fulfilment → completed | ✅ «приз передан» | — | ✅ | Подтверждение победителя или истечение срока |
| any active → suspended | — | ✅ | ✅ | Причина + уведомление |
| draft/approved/scheduled → cancelled | ✅ | — | ✅ | После `active` — только админ |
| results_published → disputed | — | ✅ (по жалобе) | ✅ | Блокирует вручение |

Правка правил после `approved` — только новой версией через повторную модерацию; участники видят версию, на которой они вошли.
