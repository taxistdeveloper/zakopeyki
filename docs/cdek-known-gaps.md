# CDEK — известные пробелы

Пробел закрыт только если есть ответ в OpenAPI этого репозитория или в коде, который этот ответ не подменяет. Юридические формулировки ниже не являются решением.

## Блокируют запуск

| Вопрос | Кто подтверждает | Что нельзя делать до ответа |
|---|---|---|
| Кто сторона договора перевозки и счетов CDEK, если API-аккаунт платформы, отправитель — продавец, заказчик доставки — покупатель | CDEK и юрист | Включать боевое создание заказов |
| Как оформляется АВР/акт и между кем | Бухгалтер и юрист | Считать сохранённый JSON актом или закрывающим документом |
| Когда и кто возвращает покупателю оплату доставки, если CDEK не вручил посылку или выполнил refusal/clientReturn | Владелец продукта, юрист, бухгалтер | Включать возврат денег. В коде его нет, и логистическая операция его не запускает |
| Можно ли платформе создавать заказ от имени покупателя и какие поля отправителя обязательны | CDEK | Менять роли в payload |

## Не закрыты спецификацией CDEK

| Вопрос | Кто подтверждает | Последствие в коде |
|---|---|---|
| Enum `OrderStatusDto.code` пустой | CDEK | Неизвестный код сохраняется, на экране «Статус уточняется» |
| При каких статусах разрешены `POST .../refusal` и `POST .../clientReturn`, чей `tariff_code` | CDEK | `mayCallCdek()` = false, кнопки скрыты |
| Схема входящего `DELIV_PROBLEM` | CDEK | Пишутся только короткий `code` и дата |
| Какой `requests[].state` означает, что refusal выполнен | CDEK | Сверка умеет читать SUCCESSFUL/INVALID/ACCEPTED, но не считает это возвратом денег |
| Лимит активных webhook-подписок | CDEK | Не регистрировать больше двух, пока нет письменного лимита |
| Подпись webhook | CDEK, в OpenAPI её нет | Свой общий token. Это не подпись CDEK |
| Шаблон накладной для Казахстана | CDEK | В enum нет KZ-шаблона, по умолчанию `tpl_russia` |
| `OrderUpdateRequestDto` / PATCH не используется для отказа | CDEK | PATCH из пользовательского сценария не вызывается |
| `deliverypoints` by polygons в OpenAPI нет | CDEK | Метод не вызывается |
| Улица для доставки до двери не сверяется со справочником CDEK | CDEK | `address_verified` остаётся false |

## Технические ограничения, не равные готовности

- Документы `docs/cdek-integration-audit.md` и начало `docs/cdek-api-client.md` описывают ранние фазы. Актуальный контур — тематические `docs/cdek-*.md` и этот файл.
- Схема меняется при первом обращении к модели (`ensureTable`), а не версионированной миграцией. На production это нужно прогнать на копии базы до переключения трафика.
- Уникальный индекс `cdek_uuid` не мешает нескольким NULL. Пустая строка вместо NULL может столкнуться.
- `bin/cdek_*` не стоят в системном cron этого репозитория. Без cron 202 и пропущенный webhook зависают, пока их не опросят.
- Сквозной сценарий в браузере и боевой sandbox-заказ в этом аудите не прогонялись.
- Платёжный контур в коде называется FreedomPay. Имя эквайринга не зашито в CDEK-клиент. Смена эквайринга — отдельная работа, здесь не делалась.
- Успешная регистрация заказа по-прежнему может поставить FSM `DELIVERY_ACCEPTED` до кода перевозки. Экран при пустом `cdek_status_code` пишет, что передача посылки не подтверждена.
